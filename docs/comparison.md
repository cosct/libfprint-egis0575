## 2. 为什么 swipe 模型精度差

1. 传感器 103×52，swipe 条带之间靠运动估计拼接——小条带的运动估计误差
   被放大，拼接图畸变直接摧毁 minutiae 提取
2. Bozorth3 在如此小的图像上本来就不可靠（EH577 作者实测结论：NBIS
   unusable，匹配分数不稳定）
3. swipe 要求用户"长划整个指尖"，笔记本电源键大小的传感器上体验极差，
   划得快/慢/歪都影响成帧

## 3. 移植自 EH577 的机制（已全部落地）

### 采集（每次轮询一个完整新鲜周期）
- PRE_INIT(29) → POST_INIT(18) 末包 `64 14 ec` 收帧；校准版驱动改为
  校准流程（protocol.md §4A），POST_INIT 语义保留为错误重试路径
- claim 回收：达到配额即 release+re-claim 接口并重传校准（EH575 上
  配额定为 200 帧/claim，§7 第 1 条）
- 启动加固：claim 后 settle 150ms；首包超时 → claim 回收重试 ≤2 次 →
  干净失败；超时统一 2000ms

### 指纹在检（软件）
- 暖背景基线：启动先收 3 个有效空帧（BACKGROUND_WARMUP_FRAMES=3），
  否则热像素 idle 帧会被误判为手指（死锁坑）
- 基线滚动更新：最近的"无指"帧持续覆盖；刷新门 std<10（EH577 的
  raw<200 门在 EH575 永假，已改）
- 判据：bg 扣除后三门（coverage ≥18% 且 intensity ≥10 且
  raw_finger_pixels ≥800 判存在；EH575 数据集验证边界干净，见
  protocol.md §6）

### 每触按（turn）状态机
- settle 400ms（手指按下稳定后才评估）；turn 超时 1400ms（单次按压绝不
  无限轮询）
- 通过质量检查的帧立即提交（fast exit）；未通过的帧直接丢弃，在 turn
  窗口内持续重试直至超时
- 录入阶段每次 accepted 后置 waiting_for_lift 状态位，直到检测到真实
  抬手才 re-arm（事件式封锁，非定时）
- 幻影在检恢复：无条件 4 秒 stuck-presence 看门狗

### 图像处理管线（顺序）
1. 全宽 103×52（EH575 无死区，§4 决策 2）
2. 暖背景扣除（`val > bg+2 ? val-bg : 0`）
3. pad 宽度到 4 的倍数（104）→ `fpi_image_resize` 2x → 208×104
4. 3×3 中值降噪（去高频噪点，保边缘）
5. stretch5 对比度拉伸：p5..p99 → 20..245
6. Stage-2 质量检查（全部通过才接受）：
   - grain < 6.000%（中值滤波残差 >25 的像素占比，×1000 存储）
   - 0 < minutiae < 10（NBIS get_minutiae；上限防噪点制造假细点）
   - ridge pixels > 4000（阈值 180 以下计为脊线）
   - 真手指通过率 86%（48/56），失败帧均为 minutiae=0（糊帧正确拒绝）

## 4. EH575 移植决策（全部定案）

| 决策点 | 结论 | 依据 |
|---|---|---|
| 基座架构 | championswimmer press | 唯一在真实小图传感器上验证可用的采集路线 |
| 初始化 | **topni1 校准流程（必须）** | 真机验证：无校准 → 全零帧（protocol.md §4B） |
| 有效宽度 | **103 全宽，无死区** | 600 帧列活跃度分析定案；EH577 的 33 列死区在 EH575 不存在 |
| swipe/press | press | §2 |
| claim 配额/回收 | 移植，配额放宽到 200 | 防死锁；更激进会挂死固件（§7） |
| settle/turn 时序 | 移植（400/1400ms） | 已调好的真机参数 |
| Stage-2 质量检查 | 移植 + EH575 数据集重调 | 通过率 86%，糊帧正确拒绝 |
| 匹配器 | **Windows 引擎移植**（弃 NCC） | §5 七方案全败 → §6 引擎移植达标 |

## 5. 匹配器实验史：七个方案为何全败（2026-09-12）

同一数据集（同人左右食指、位置多样模板库、多帧 probe）上，所有经典
匹配方案无法区分真假：

| 匹配器 | 真手指 best 分数 | 冒充 best 分数 | 结论 |
|---|---|---|---|
| NCC（±30 窗，多帧最佳） | 0.36–0.96 | 0.38–0.80 | 重叠，冒充可高至 0.80 |
| 掩码 NCC（非零并集） | 0.36–0.67 | 0.38–0.70 | 与普通 NCC 无差异 |
| Bozorth3（2x，4–10 细点） | ~0 | 0–7 | 细点太少，共识匹配失败 |
| Bozorth3（4x，54 细点） | 0 | 0–7 | 细点为增强伪影，帧间不可重复 |
| POC / BLPOC | 0.05–0.29 | 0.04–0.34 | 完全重叠 |
| 方向场（结构张量块方向） | 0.023–0.026 | 0.019–0.026 | 完全重叠 |
| SigFM（SIFT+Lowe+几何投票） | — | — | 跨按压 Lowe 通过仅 2–4 对（<5 下限）；自匹配 3.5 亿票证明移植正确 |

**根因（原始帧统计实证）**：按压帧原始灰度 std 仅 3.0（空帧 2.7）——
脊线可见度完全由驱动管线（背景扣除+拉伸）合成，原始信号信噪比极低。
一切依赖"自然纹理可重复性"的描述子（SIFT/细点）都没有原料；一切
全局相关性（NCC/POC）又被同人食指的结构相似性淹没。

注：EH577 作者的 NCC 匹配器大概率存在同样的 FAR 问题（其未发表
同人不同指测试数据）。

## 6. Windows 引擎移植：终局方案

时间线：反编译架构还原（2026-09-13 从 Animeshz Ghidra 档案）→ 系数表
提取（EgisTouchFPEngine0575.dll，签名扫描定位，见
windows-engine-tables.md）→ Python 复刻迭代（离线数据集完美分离）→
C 移植入驱动（`egis0575-matcher.c`，纯 C 无 GLib，独立可测）。

### 引擎管线（全部参数可溯源到 DLL）
1. 平场归一化 → **11 取向脊线匹配 FIR 滤波器组**（抽头提取自 DLL）
   → 增强图 + 取向图
2. 滤波响应严格局部极大值兴趣点 + 密度 NMS（跨按压几何重复性 52%）
3. 512bit 顶档描述子：4×4 区域 × 32 方向 bin，DLL 金字塔权重，
   主方向 = 获胜滤波取向
4. 海明最近邻（预算 115/512，无 Lowe）→ 平移簇聚类（匹配位移按
   8px 桶取众数，非迭代 RANSAC）→ 角度众数投票
5. Windows 评分 Σ(128−hamming) − 未匹配特征惩罚(h/2)
6. **双帧模板库一致性**（对抗位置特异偶然对齐）

### 验证数字（证据强度说明见本节末尾）
- **离线**（Python 复刻，判据 = 单帧最佳 ≥244 且 ≥2 帧模板库一致 ≥150）：
  真A/真C 全过，假A/假C 全拒（含 438 高分假对被 1 帧一致击杀）——
  FRR 0%（6/6），FAR 0%（0/12）
- **C 移植标定**：C 引擎的描述子位与 Python 参考略有差异（平场边界
  处理 + 取向滤波插值路径不同），分数标度不同。**2026-09-13 重标定**
  （取向4 核修正等修复后，23 个 verify-run 共 125 个 probe，按运行取
  最高单帧分）：可信真手指运行最低 349、可信冒充运行最高 288（含存疑
  运行 321）→ **阈值 335（区间中点）**，agree ≥2 帧 × ≥150 不变。
  （修复前旧引擎：真 336–470 / 假 127–280 / 阈值 300，已作废）
- **真机集成验收**（2026-09-13，修复前引擎 + v0 模板）：右食指 ×3 =
  622/404/381 全 MATCH（早退判定 ~2s）；左食指冒充 = 285 正确拒绝。
  修复引擎与 v1 模板（恢复取向字段）下需重录重验
- **系统级**（fprintd 全链路，修复前引擎 + 旧阈值 300——现行阈值 335，见 §9；待重测）：`probes=1 best_score=1086/300 => MATCH`

**证据强度**：以上为小样本单机验证——6 个同人按压组 / 12 个异人比较、
阈值在同一批数据上调出、单台 EH575 机型；未做独立留出集、多机型与
FAR@FRR/EER 曲线。数字应理解为"小样本验证通过"，不是统计意义上的
FRR/FAR 声明。扩样本评估（含可去标识化测试向量与评测脚本）见 §9。

### 与 Windows 原版的差异
Windows 原版阈值为 660（自适应 −80/+60 封顶 1.5x）；本驱动因 C 移植
分数标度不同改用固定 335 + 双帧一致（2 帧 × ≥150）。自适应阈值仍
未移植；验证期模板回馈（加密注册表 blob 'AE' 的对应物）已实现
**进程内内存版**（2026-09-14）：高置信匹配（≥阈值+30）的 probe 帧
回授进内存模板库（每指纹上限 16 帧 = 12 录入 + 4 回授，FIFO 只淘汰
回授帧；同点帧按录入相似阈值去重），随 fprintd 进程生命周期有效——
fprintd 默认空闲 30s 退出，跨解锁会话保留需让 fprintd 常驻
（systemd drop-in：`ExecStart=` 置空后 `ExecStart=/usr/lib/fprintd -t`，
代价是传感器持续低速轮询，由 §7 第 8 条看门狗兜底）。FAR 影响：
冒充分离余量 47 分的标定在 12 帧模板库上做出，16 帧上限等于多发
4 张"彩票"，回授门槛 365 相对冒充峰值 288 有 77 分缓冲；扩样本后
需复核。

## 7. 稳定性工程成果（全部真机验证）

1. 校准链路（读校准→复位→上传→POST_CAL 轮询）稳定出图
2. claim 配额回收 + 校准重传：从 6 帧/claim 放宽到 200（每 130ms 一次
   重传的重压 3.5 分钟内 1865 次导致固件挂死——200 是安全上限内的
   工作点）
3. 采集结束关闭序列（topni1 POST_REPEAT，含 AGC/曝光 `71` 族）：
   防止传感器滞留连续采集模式导致按压失灵（两次复现）
4. 幻影在检恢复：背景刷新门 std<10（EH577 的 raw<200 门在 EH575 永假）
   + 无条件 4 秒 stuck-presence 看门狗
5. 优雅关闭（延迟到采集循环收尾再释放接口）+ SIGINT 化测试脚本
6. USBDEVFS_RESET 软复位（scripts/reset-sensor.sh）从端点残留/挂死恢复
7. 帧读取挂死时 2s 超时不触发、SIGINT 链失效 → 只能 kill -9 + 复位，
   根因与固件疲劳相关，关闭序列（第 3 条）为主要缓解
8. 长会话渐进失敏（>10 分钟轮询 coverage 50%→2–5%）→ **驱动内看门狗已随
   v0.2.0 实现**：10 分钟预防性完整重初始化 + weak-press 失敏检测（8 秒
   窗口 ≥8 帧，2026-09-16 从 20 下调：间歇重按的轻度失敏也要能触发）
   → 回收 claim + 重跑校准链自动恢复；见 §7 第 7 条的硬挂死
   场景仍用 USBDEVFS_RESET 手动恢复

## 9. 遗留问题

1. identify（1:N）能否安全启用——模板库数量上限未测
2. 冒充分离余量经重标定为 47 分（可信冒充峰值 288 vs 阈值 335；
   4 个存疑运行的峰值 321 未归类，需补标签）——继续扩数据集收紧
3. 帧读取硬挂死（2s 超时都不触发、SIGINT 链失效，§7 第 7 条）时的自动
   USBDEVFS_RESET——失敏看门狗已在驱动内实现（§7 第 8 条）；校准块损坏
   （含 2026-09-14/15 实测的全零块形态：固件后台秒~分钟级重建）已由
   自动恢复覆盖（立即重读 → 模板内嵌副本 → 1Hz 耐心重读，上限 7 次，
   见 protocol §8 第 3 条）；帧读取硬挂死此极端场景
   仍需手动 scripts/reset-sensor.sh
4. 长时匹配阈值自适应（Windows 有，未移植）
5. 上游化补丁整理（含 matcher 独立文件 + 协议文档），目标
   [libfprint 上游](https://gitlab.freedesktop.org/libfprint/libfprint)
